| 9 | 3 | 3 | **No automated tests for `world-server`/`gateway` netcode.** `Player.cs`, `WorldStore.cs`, message dispatch in `Program.cs`, and voyage ticket claim/expiry in `gateway/Program.cs` have zero coverage — only `sim-core` (the pure-rules library) is tested. Tonight's interest-management fix was verified by hand with a throwaway two-client LiteNetLib harness (see `LOG.md` 2026-08-14) because no reusable harness/test project existed. Turn that harness into `tests/world-server.tests` — a small helper that boots an in-memory-mode world-server on a random port and drives it with raw LiteNetLib clients — so future netcode changes get a real regression test instead of a one-off script. |
| 9 | 3 | 3 | **No chunk streaming as the player roams.** `World3D.Build()` generates a fixed `Radius=2` (5×5 = 320m×320m) area once, at world load, and never grows it as the player walks away from origin — there is no re-request-on-move logic in `World3D.cs` or `WorldConnection.cs`. Already flagged in code as "this first slice," so likely known, but worth a decision: either scope the alpha to a bounded playable radius on purpose (document it) or implement chunk streaming (client requests chunks within N of its tile, unloads chunks that fall out of range — mirrors the interest-management pattern just added server-side for players). |
| 6 | 2 | 3 | **`TileChanged` / `HarvestProgress` / `StructurePlaced` are not interest-filtered.** Same invariant gap as the `PlayerStates` broadcast fixed tonight, but lower urgency: these are event-driven (fires once per player action), not per-tick, so bandwidth grows with world activity rather than with `players²` continuously. Worth applying the same `World.IsWithinInterest` check once chunk streaming (above) makes "near" well-defined for terrain events too — right now every player sees every harvest/build/felled-tree in the *entire* world, which is also a minor immersion problem (announcing far-away activity) independent of bandwidth. |
| 4 | 2 | 2 | **`SurvivalHud.cs` (940 lines) and `World3D.cs` (735 lines) exceed the 400-line god-script line.** Not a coupling problem — both are cohesive, single-purpose, and laid out in named regions — but `SurvivalHud` in particular could split cleanly along its existing tab boundaries (`BuildInventoryTab`/`BuildCraftTab`/`BuildPlaceTab`/`BuildTravelTab` each becoming its own small `Control`-derived class) if it grows further. Not urgent; revisit if a new tab or HUD panel is about to be added. |
| 4 | 2 | 2 | **`RequestChunk` has no per-connection rate limit.** A client can request arbitrarily many chunk coordinates per second; each costs a `TerrainGenerator` pass server-side. Not exploitable for anything worse than wasted CPU today (single-player-scale testing, no adversarial traffic expected yet), but worth a cheap per-peer token bucket before this is ever exposed beyond a LAN/dev environment. |
| 3 | 3 | 1 | **`character.inventory` JSONB has no schema-version field.** Item stacks are keyed by stable `ItemId` enum name (robust to renumbering), but there's no explicit version to detect a future *shape* change (e.g., per-item metadata instead of a flat count). Add a `schema_version` column proactively before the shape needs to change, so the eventual migration has something to branch on instead of sniffing JSON shape.
